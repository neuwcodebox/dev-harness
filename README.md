# {{PROJECT_NAME}}

AI와 함께 프로젝트를 개발하고 이어가기 위한 워크스페이스 템플릿이다. 목표·설계·현재 상태를 저장소에 남기되, 별도 생성기나 강제 워크플로는 두지 않는다.

**현재 상태: 프로젝트 초기화 전. 제품 코드와 실행 환경은 아직 없다.**

## 시작하기

이 폴더를 새 프로젝트의 작업 루트로 복사하고 아래 프롬프트와 프로젝트 설명을 개발 AI에게 전달한다. 기존 프로젝트에 적용한다면 이 파일들을 그대로 덮어쓰지 말고, 템플릿을 참고 자료로 제공해 기존 문서와 통합하게 한다.

### 프로젝트 시작 프롬프트

```text
이 워크스페이스를 아래 프로젝트에 맞게 초기화해 줘.

먼저 AGENTS.md와 docs/SPEC.md, TECH.md, PLAN.md를 읽고, 기존 코드와
사용자 변경이 있으면 보존하면서 현재 상태를 파악해.
내가 제공한 설명과 이미 정한 결정을 우선하고, 같은 정보를 다시 묻지 마.
목표·범위·권한을 결정하는 데 꼭 필요한 정보만 질문하고,
나머지 불확실성은 가정이나 미정 사항과 확인 방법으로 남겨.

SPEC에는 목적·핵심 사용 흐름·범위·수용 기준을,
TECH에는 실제 제약과 기술 선택·구성·중요한 근거를,
PLAN에는 현재 상태·의미 있는 단계·바로 이어갈 다음 작업을 담아.
기술 선택이나 지원 여부를 확정하려면 관련 공식 자료나 실제 코드를 확인해.
문서에 적혀 있다는 이유만으로 구현되었거나 검증되었다고 취급하지 마.

AGENTS.md는 짧은 판단 기준과 문서 안내로 유지해.
프로젝트별 사실과 상세 절차는 해당 문서에 한 번만 두고,
기존 내용과 맞지 않는 부분은 덧붙이기보다 수정·통합해.
불필요한 규칙, 문서, 빈 구현 디렉터리, 개발 도구는 추가하지 마.

README는 프로젝트 소개·준비·실행·개발 방법으로 바꾸고,
실제로 존재하는 명령만 기록하며 실행 확인 여부를 구분해.
아직 없는 실행·검증 명령은 '아직 없음'으로 남겨.
.gitignore는 실제 기술 스택에 맞게 조정하되 lockfile이나
공유할 설정을 무심코 제외하지 마.

초기화가 끝나면 모든 {{...}} placeholder, 작성 안내 주석,
불필요한 예시와 이 시작 절차를 제거해.
알 수 없는 값은 억지로 채우지 말고 미정인 이유와 다음 행동을 남겨.
이미 초기화된 프로젝트라면 초기 상태로 되돌리지 말고 필요한 차이만 반영해.

이번 요청은 하네스 초기화까지다. 제품 기능 구현이나 실행 환경 변경은 하지 마.
문서의 목표·설계·계획이 일치하고 링크가 연결되는지 살핀 뒤,
무엇을 확정했고 무엇이 미정인지, 다음 개발 작업이 무엇인지 알려줘.

프로젝트 설명:
여기에 만들려는 것, 사용자와 사용 상황, 이미 정한 방향,
운영 환경·제약, 참고 자료를 자유롭게 적는다.
모르는 항목을 형식에 맞추려고 억지로 채울 필요는 없다.
```

프로젝트 설명을 같은 대화에서 이미 전달했다면 마지막 부분 대신 그 설명을 사용하도록 요청하면 된다. 초기화 완료 후에는 README를 포함한 문서들이 해당 프로젝트의 문서로 바뀌며, 시작 프롬프트는 원본 템플릿에만 남는다.

### 초기화 완료의 기준

목표와 범위, 사용자 관점의 수용 기준이 분명하고 TECH의 선택과 PLAN의 다음 작업이 이를 뒷받침해야 한다. 남은 불확실성은 숨기지 않는다. placeholder와 작성 안내가 제거되고 문서 링크가 유효해야 하며, 코드가 없는 상태를 실행 가능한 제품으로 표현하지 않는다.

## 문서 구성

```text
project/
├── AGENTS.md
├── README.md
├── .gitignore
└── docs/
    ├── SPEC.md
    ├── TECH.md
    ├── PLAN.md
    └── history/
```

| 문서 | 이 문서가 소유하는 내용 |
| --- | --- |
| [AGENTS.md](AGENTS.md) | AI의 판단 기준과 문서 탐색 안내 |
| [README.md](README.md) | 사용·설치·실행·개발 방법과 실제 명령 |
| [SPEC.md](docs/SPEC.md) | 목적, 사용자 요구, 범위, 수용 기준 |
| [TECH.md](docs/TECH.md) | 현재 설계, 구성 경계, 기술 선택과 근거 |
| [PLAN.md](docs/PLAN.md) | 현재 진행 상태, 남은 일, 다음 행동 |
| [history/](docs/history/) | 중요한 작업의 변경·판단·검증 기록 |

`history/`는 비워 두었다. 새 작업 기록은 시작 날짜와 주제가 드러나는 파일명으로 만들고, 여러 날 이어지는 같은 작업은 같은 파일에 시점을 구분해 기록할 수 있다. 목적·변경·결정 이유·검증 환경과 명령·결과·남은 문제 중 필요한 내용만 담는다. 원시 로그를 전부 복사하거나 별도 인덱스를 관리할 필요는 없다.

## Placeholder

| 값 | 의미 | 작성 위치 |
| --- | --- | --- |
| `{{PROJECT_NAME}}` | 프로젝트 이름 | README·AGENTS 제목 |
| `{{PROJECT_GOAL}}` | 해결할 문제와 목표 | SPEC |
| `{{PROJECT_SCOPE}}` | 이번 범위와 제외 범위 | SPEC |
| `{{CONSTRAINTS}}` | 운영 환경과 실제 제약 | SPEC |
| `{{TECH_DECISIONS}}` | 채택한 기술·설계 방향, 아직 미정인 선택 | TECH |

이 값들은 초기화를 돕는 표식이지 설정 시스템이 아니다. 단순 치환으로 끝내지 말고, 주변 내용과 작성 틀까지 프로젝트에 맞게 정리한다. `{{...}}` 형식은 제품 코드나 정상 예시가 아니라 이 템플릿의 미작성 표시로 사용한다.

## 실행·개발 명령

아직 제품 코드와 도구가 없으므로 실행·테스트·빌드 명령도 없다. 초기화 시 기존 명령이 있으면 실행 위치와 필요한 환경, 확인 여부를 함께 기록한다. 명령이 생기기 전까지 가상의 `npm test` 같은 예시를 실제 명령으로 등록하지 않는다.

## 다음 세션에서 이어가기

초기화한 프로젝트에서는 다음처럼 요청하면 된다.

> AGENTS.md와 docs/PLAN.md를 읽고 현재 목표에 맞는 다음 작업을 진행해. 관련 SPEC·TECH·코드·이력만 추가로 확인하고, 변경 영향에 맞춰 검증한 뒤 다음 세션이 이어갈 수 있게 정리해.

## 템플릿 유지

템플릿은 새 프로젝트의 출발점이다. 사용 중인 프로젝트에는 새 템플릿을 통째로 덮어쓰지 않고 필요한 개선만 기존 맥락에 맞게 반영한다. 반복되는 실제 문제가 있을 때 가장 작은 수정으로 개선하며, 공통 도구나 문서를 미리 늘리지 않는다.
